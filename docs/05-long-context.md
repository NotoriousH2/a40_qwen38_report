# 05. 장문 컨텍스트 — 64K 이상을 개발에 쓰려면

용도가 개발이라 컨텍스트가 64K 이상 필요하다는 요구에서 출발한 분석입니다.
docs/04 의 31K 수치가 신뢰할 수 없다는 것을 발견한 뒤 측정 방법을 바꿔 다시 잰 결과입니다.

- 재현: `bench/longctx2.py` (합성 텍스트), `bench/realcode.py` (실제 C++ 소스)
- 원본: `results/results_longctx2.json`, `results_realcode.json`
- 측정법: `/completion` + `ignore_eos:true` + `n_predict` 고정 → decode 속도를 안정적으로 측정

## 컨텍스트 길이별 곡선

Q3_K_XL, DFlash2 n-max 4, `-c 131072`, `-np 1`, `-ub 256`, 256토큰 생성.

### f16 KV

| 컨텍스트 | prompt_n | prefill | prefill 소요 | decode† |
|---|---|---|---|---|
| 8K | 7,980 | 997 tok/s | 8.0초 | 93.50 |
| 32K | 32,000 | 965 tok/s | 33.2초 | 93.80 |
| 64K | 64,000 | 851 tok/s | 75.2초 | 87.37 |
| 110K | 109,990 | 737 tok/s | 149.2초 | 78.56 |

### KV 타입 비교 (같은 조건)

| 컨텍스트 | f16 | q8_0 | q4_0 | 투기 끔(f16) |
|---|---|---|---|---|
| 8K | 93.50 | 86.78 | 88.81 | 34.31 |
| 32K | 93.80 | 83.36 | 84.91 | 31.45 |
| 64K | 87.37 | 72.53 | 74.65 | 28.24 |
| 110K | 78.56 | 60.31 | 63.01 | — |

† **주의**: 이 표의 decode 는 반복적인 filler 텍스트로 측정해 acceptance 가 1.000 으로
부풀어 있습니다. **최선값**으로만 읽으세요. 현실적인 수치는 아래 실제 코드 벤치를 보세요.
(→ [docs/07](07-measurement-pitfalls.md))

## 실제 코드로 재측정

llama.cpp 의 실제 C++ 소스 64,020 토큰을 컨텍스트로 넣고 256토큰씩 생성했습니다.

| 설정 | Q1 (콜드) | Q2 | Q3 | acceptance |
|---|---|---|---|---|
| **DFlash2 + f16 KV** | **55.74** | 47.78 | 48.55 | 0.578 / 0.432 / 0.443 |
| DFlash2 + q8_0 KV | 34.22 | 39.40 | 43.92 | 0.352 / 0.424 / 0.504 |
| 투기 끔 + f16 KV | 28.12 | 28.13 | 28.16 | — |

**64K 에서도 DFlash2 는 1.7~2배 이득입니다.** docs/04 의 31K 열을 근거로 한 초기 결론
("장문에서 42% 손해")은 틀렸습니다. 자세한 경위는 docs/07.

## 진짜 병목은 prefill 이다

decode 는 110K 에서도 79 tok/s 로 멀쩡합니다. 문제는 **64K 를 한 번 넣는 데 75초,
110K 면 149초**라는 것입니다.

그리고 이건 튜닝으로 개선되지 않습니다.

- `-ub` 를 256→2048 로 올려도 무변화 (docs/04)
- prefill 737~1116 tok/s 는 A40 에서 27B Q3 모델의 하드웨어 한계 근처입니다.
  대략 계산하면 토큰당 2×27e9 ≈ 54 GFLOP, 950 tok/s 면 약 51 TFLOPS.
  A40 의 bf16 텐서코어 이론치 약 150 TFLOPS 대비 **MFU 34%** 로, 양자화 역양자화 오버헤드를
  감안하면 llama.cpp 로서는 정상 범위입니다.

## 해법: 두 번 하지 않기

`--cache-reuse 256` 으로 프리픽스를 KV shifting 재사용합니다.

```
같은 64K 프리픽스, 뒤쪽 질문만 교체:
  1회차   prompt_n = 60,009    69.3초
  2회차   prompt_n =    262     0.7초      ← 99배
  3회차   prompt_n =    259     0.7초
```

개발 워크플로는 "같은 코드베이스 + 바뀌는 질문"이라 이 패턴에 정확히 맞습니다.

> **프롬프트 구성 규칙**: 고정 컨텍스트(코드베이스)를 **앞쪽**에, 바뀌는 질문을 **뒤쪽**에.
> 앞쪽이 한 토큰이라도 바뀌면 캐시가 깨져 다시 70초를 냅니다.

`--slot-save-path` 를 함께 주면 슬롯 KV 를 디스크에 보존할 수 있습니다
(이번 실험에서 재시작 후 복원까지는 실측하지 않았습니다).

## 최종 구성과 검증

남는 VRAM 을 슬롯 수에 투자했습니다. `-c 262144 -np 2` → **슬롯당 131,072 × 2**.
두 세션이 각자의 프리픽스 캐시를 유지합니다.

```
model  : Qwen3.8-27B-UD-Q3_K_XL.gguf
n_ctx  : 131072 (슬롯당) × 2 슬롯
VRAM   : 31,465 / 46,068 MiB       (14.6 GB 여유)

60K 실제 코드 컨텍스트:
  turn1  prompt_n=60,009  prefill 69.7초  decode 65.41 tok/s  acc 0.679
  turn2  prompt_n=   262  prefill  0.7초  decode 67.39 tok/s  acc 0.704
  turn3  prompt_n=   259  prefill  0.7초  decode 86.34 tok/s  acc 0.990
```

→ `scripts/run-server-dev.sh`

## 남은 레버

가장 큰 것은 **컨텍스트를 정말 64K씩 넣어야 하는가** 입니다. prefill 이 길이에 선형이라
관련 파일만 20K 로 추리면 75초가 23초가 됩니다. 캐시가 있어도 첫 진입 비용은 남습니다.
