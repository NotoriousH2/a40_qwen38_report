# 06. 양자화 등급 결정 — Q3_K_XL vs Q4_K_XL

VRAM 이 14GB 남으니 양자화 등급을 올리는 게 자연스러워 보였습니다. 재보니 손해였습니다.

- 재현: `bench/compare_quant.py`
- 원본: `results/perplexity.txt`

## 속도 비교 (동일 프로파일, 동일 스크립트)

두 모델 모두 `-c 262144 -np 2`, f16 KV, `--cache-reuse 256`, DFlash2 n-max 4.
같은 스크립트를 모델만 바꿔 실행했습니다.

| | Q3_K_XL (13.1 GB) | Q4_K_XL (17.6 GB) | 차이 |
|---|---|---|---|
| 짧은 ctx 384토큰 | **70.7** tok/s | 52.0 tok/s | **-26%** |
| 60K 코드, 1회차 | **65.4** tok/s | 41.8 tok/s | **-36%** |
| 60K 코드, 2회차 | 67.4 | 65.9 | -2% |
| 60K 코드, 3회차 | 86.3 | 64.4 | -25% |
| 60K prefill | 69.7초 | 70.6초 | 동일 |
| acceptance (짧은 ctx) | 0.609 | 0.465 | 하락 |
| VRAM | 31.5 GB | 35.6 GB | +4.1 GB |

prefill 이 동일한 것이 단서입니다. prefill 은 연산 병목이라 가중치 크기에 둔감하고,
decode 는 대역폭 병목이라 민감합니다.

**예상보다 손실이 컸던 이유**는 대역폭만이 아닙니다. 가중치 비율은 17.6/13.1 = 1.34배인데
실제 손실은 26~36%였습니다. Q4 에서 **draft acceptance 가 오히려 떨어져서**(0.609 → 0.465)
투기 효율 저하가 겹쳤습니다.

## 품질 비교 — 코드 perplexity

속도를 지불하는 이유는 품질이므로 그걸 재지 않으면 판단이 안 됩니다.
코딩 용도에 맞는 프록시로 llama.cpp 의 실제 C++ 소스를 평가 텍스트로 썼습니다.

```bash
llama-perplexity -m <model>.gguf -f eval_code.txt -c 4096 -ngl all -fa on --chunks 60
```

```
Q3_K_XL   PPL = 1.6866 ± 0.00689
Q4_K_XL   PPL = 1.6707 ± 0.00678
          차이 = 0.0159  (-0.94%)
```

오차 범위(합산 약 ±0.0097)보다 크므로 실재하는 차이입니다. 다만 **0.94%** 입니다.

## 결론

**Q3_K_XL 을 쓰세요.** 품질 0.94% 개선에 디코딩 26~36% 와 VRAM 4.1GB 를 지불하는 것은
대화형 개발 워크로드에서 명백히 손해입니다.

> **정직하게 덧붙이면**, perplexity 는 코딩 능력의 약한 대리 지표입니다. 긴 코드를 문법적으로
> 정확히 뽑아내는 능력 같은 것은 0.9% ppl 차이에 잘 잡히지 않을 수 있습니다.
> 다만 속도 대가가 이 정도로 크면 그 불확실성을 감안해도 Q3_K_XL 이 맞다고 판단했습니다.
> 실제 코딩 벤치마크로 재검증하는 것은 남은 과제입니다.

Q4_K_XL 로 바꿔보려면 모델만 교체하면 됩니다.

```bash
ALT=1 ./scripts/download-models.sh
TARGET=$MODEL_DIR/Qwen3.8-27B-UD-Q4_K_XL.gguf ./scripts/run-server-dev.sh
```

Q5 / Q6 등 중간 등급은 재보지 않았습니다. 곡선상 Q3 과 Q4 사이 어딘가가 더 나은 절충점일
가능성은 남아 있습니다.
