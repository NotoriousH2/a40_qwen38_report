# 04. 튜닝 스윕 — 16개 조건 전체

남는 VRAM 27GB를 어디에 쓸지 결정하기 위한 실험입니다.
설정마다 서버를 새로 띄우고 동일 프롬프트로 측정했습니다.

- 재현: `bench/sweep.py`, `bench/sweep2.py`, `bench/sweep3.py`
- 원본: `results/results.json`, `results2.json`, `results3.json`
- 설정별 서버 로그: `results/logs/<이름>.log`

**측정 조건** — 모델 Q3_K_XL(별도 표기 없으면), `-c 131072`, `-np 1`, `-b 2048`, `-ngl all`, `-fa on`.
"짧은 ctx" = 384토큰 생성 3회의 중앙값(`predicted_per_second`).
"31K ctx" = 31,220토큰 프롬프트 이후 디코딩.

> ⚠️ **이 표의 `31K ctx` 열은 신뢰하지 마세요.** 해당 프롬프트가
> `Reply with the single word: OK` 로 끝나 실제 생성이 2~3토큰뿐이었습니다.
> 자세한 내용과 올바른 수치는 [docs/07](07-measurement-pitfalls.md), [docs/05](05-long-context.md).
> 같은 조건끼리의 **상대 비교**로만 쓰세요.

## 읽어낸 것

### `-ub` 는 아무 효과가 없다

```
-ub  256 → prefill 951 tok/s,  VRAM 19,117
-ub 1024 → prefill 962 tok/s,  VRAM 20,267
-ub 2048 → prefill 939 tok/s,  VRAM 21,801
```

오차 범위입니다. **설정이 안 먹힌 게 아닙니다** — VRAM 이 ubatch 에 비례해 정확히 늘어난 것이
그 증거입니다. 그냥 prefill 병목이 아니었습니다. 병목이 무엇인지는 docs/05.

→ **`-ub 256` 유지.** 올리면 VRAM 만 2.7GB 낭비합니다.

### n-max 를 올리면 느려진다

drafter 의 `block_size` 가 8이라 8까지 올리면 이득일 것으로 예상했지만 반대였습니다.

| n-max | 짧은 ctx | acceptance | draft당 채택 |
|---|---|---|---|
| 2 | 62.1 | 0.785 | 1.57 |
| 3 | 67.5 | 0.687 | 2.06 |
| **4** | **67.0** | 0.564 | 2.24 |
| 6 | 61.4 | 0.451 | 2.70 |
| 8 | 58.0 | 0.408 | 2.85 |

draft당 채택 토큰은 늘지만 **acceptance rate 가 무너져** verify 연산 낭비가 더 큽니다.
f16 KV 에서 다시 재도 꼭짓점은 4입니다 (n3/n4/n5/n6 = 68.2 / **75.6** / 72.2 / 67.9).

PR 저자가 보고한 acceptance 5.0은 Apple M5 Pro 기준이며 이 조합에서는 재현되지 않았습니다.

→ **`--spec-draft-n-max 4` 유지.**

### KV 를 f16 으로 바꾸면 빨라진다 (이번 스윕의 최대 발견)

메모리를 **더** 쓰는데 **더** 빨라집니다.

```
q8_0 KV, n4 :  67.0 tok/s,  acceptance 0.564,  19,117 MiB
f16  KV, n4 :  75.6 tok/s,  acceptance 0.663,  22,465 MiB   (+13%, +3.3GB)
```

원인은 acceptance 입니다. **KV 양자화 오차가 드래프터와 타깃의 예측을 어긋나게 만들고 있었습니다.**
f16 으로 오차를 없애니 draft 가 더 자주 통과하고, 결과적으로 속도와 품질이 같이 올라갑니다.

이 효과는 투기 디코딩이 켜져 있을 때만 나타납니다. 끄면 오히려 q8_0 이 근소하게 빠릅니다
(G 27.6 vs L 26.6) — KV 트래픽이 줄기 때문입니다.

→ **`--cache-type-k f16 --cache-type-v f16`.**

### DFlash2 자체의 이득

```
짧은 ctx :  35.3 (끔) → 67.0 (켬)  = 1.90배
```

투기 디코딩은 이 구성의 핵심입니다. 장문에서의 거동은 docs/05 를 보세요
(이 표의 31K 열로 판단하면 안 됩니다).
