# 07. 측정 함정과 정정 이력

이 실험에서 측정을 두 번 틀렸습니다. 둘 다 같은 함정을 다시 밟기 쉬운 종류라 따로 남깁니다.
**결론 표만 보고 재현하려는 사람이 가장 먼저 읽어야 할 문서입니다.**

---

## 함정 1 — 짧은 생성으로 투기 디코딩을 재면 안 된다

### 무슨 일이 있었나

docs/04 스윕에서 장문 컨텍스트 성능을 재려고 이런 프롬프트를 썼습니다.

```python
prompt = ("Unified memory bandwidth bounds decode throughput ... " * 2600)
         + "\nReply with the single word: OK"
```

모델은 시키는 대로 `OK` 라고 답했습니다. **생성 토큰이 2~3개** 였습니다.
그 위에서 `predicted_per_second` 를 읽었으니, 측정된 것은 디코딩 속도가 아니라
**스텝당 고정 오버헤드**였습니다.

투기 디코딩은 스텝마다 draft 생성 + verify 라는 고정비를 냅니다. 생성이 길면 이 비용이
채택 토큰들로 분산되지만, 2~3토큰이면 고정비만 남습니다. 그래서 이런 결과가 나왔습니다.

```
31K ctx:  투기 켬 15.9 tok/s  vs  투기 끔 27.6 tok/s
```

여기서 **"장문에서는 DFlash2 를 꺼야 한다 (42% 손해)"** 는 결론을 냈습니다. 틀렸습니다.

### 제대로 재면

`/completion` + `ignore_eos: true` + `n_predict` 고정으로 생성 길이를 강제하고,
실제 C++ 소스 64K 를 컨텍스트로 넣어 다시 쟀습니다.

```
64K 실제 코드, 256토큰 생성:
  DFlash2 + f16 KV   47.8 ~ 55.7 tok/s
  투기 끔            28.1 tok/s          → DFlash2 가 1.7~2배 빠름
```

**결론이 정반대로 뒤집혔습니다.**

### 규칙

> decode 속도는 **최소 256토큰 이상** 생성해서 재세요.
> `/completion` + `"ignore_eos": true` + `"n_predict": 256` 을 쓰면 확실합니다.
> 채팅 엔드포인트로 재면 모델이 짧게 답해버릴 수 있습니다.

## 함정 2 — 반복 텍스트로 컨텍스트를 만들면 acceptance 가 부풀어 오른다

### 무슨 일이 있었나

함정 1을 고친 뒤에도 문제가 남았습니다. 컨텍스트 filler 로 같은 문장을 수천 번 반복했더니
드래프터가 다음 토큰을 완벽하게 맞혔습니다.

```
   8K   decode 93.50 tok/s   acc=1.000
  32K   decode 93.80 tok/s   acc=1.000
  64K   decode 87.37 tok/s   acc=1.000
 110K   decode 78.56 tok/s   acc=1.000
```

acceptance 1.000 은 현실에 없는 값입니다. 이 수치들은 **최선값**이지 기대값이 아닙니다.

### 제대로 재면

llama.cpp 저장소의 실제 C++ 소스를 붙여 64K 컨텍스트를 만들었습니다.

```
acceptance  0.43 ~ 0.68      decode  47.8 ~ 65.4 tok/s
```

절대값이 크게 내려왔습니다. 다만 **설정 간 상대 순서는 바뀌지 않았습니다**
(f16 > q8_0 > 투기 끔). 그래서 docs/04, docs/05 의 비교 결론 자체는 유효합니다.

### 규칙

> 컨텍스트 filler 는 **실제 코드나 문서**를 쓰세요 (`bench/realcode.py` 참고).
> 반복 텍스트를 쓸 거라면 그 수치는 상한선으로만 해석하세요.

## 부수 함정 — 프리픽스 공유로 인한 캐시 오염

길이별 곡선을 잴 때 32K / 64K / 110K 프롬프트를 같은 문장의 반복으로 만들면,
**32K 프롬프트가 64K 프롬프트의 접두사**가 됩니다. 프롬프트 캐시가 이걸 재사용해서
`prompt_n` 이 요청한 길이보다 작게 찍힙니다.

```
100K 요청인데 prompt_n=71,060  ← 앞선 31K 가 캐시에서 재사용됨
```

`bench/longctx2.py` 는 크기별로 다른 태그를 넣어 접두사 공유를 막았습니다.
반대로 **캐시 재사용을 측정할 때는 일부러 접두사를 공유**시켜야 합니다 (같은 파일의 `reuse` 측정).

---

## 부수 함정 — 프롬프트 토큰 수를 글자 수로 추정하지 말 것

`filler()` 의 토큰 수를 줄당 24토큰으로 어림했는데 실제로는 약 32토큰이었습니다.
결과적으로 "32K" 요청이 42,685 토큰, "100K" 요청이 133K 토큰이 되어 `n_ctx` 131,072 를
초과했고 **HTTP 400** 이 났습니다.

`/tokenize` 엔드포인트로 실제 토큰 수를 확인하고 이진 탐색으로 자르는 방식으로 고쳤습니다
(`bench/longctx2.py` 의 `make()`).

## 정정 요약

| 최초 결론 | 정정된 결론 | 원인 |
|---|---|---|
| 장문에서 DFlash2 는 42% 손해 | **64K 에서도 1.7~2배 이득** | 함정 1 |
| 장문 decode 78~94 tok/s | **실제 코드로는 48~65 tok/s** | 함정 2 |
| `-ub` 를 올리면 prefill 개선 | **무변화** (이건 예측이 틀린 것, 측정은 정상) | — |
| n-max 를 8로 올리면 이득 | **더 느려짐** (이것도 예측이 틀린 것) | — |

앞의 둘은 측정이 틀린 것이고, 뒤의 둘은 측정은 옳았으나 예측이 틀린 것입니다.
